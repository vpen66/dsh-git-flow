# dsh-git-flow

DeepSeek Harness 插件：**自定义 Git 工作流模板**。把「从哪个分支拉、合到哪些分支、顺序如何」
做成可编辑的模板，用鼠标点几下执行，不用记分支名和命令。

## 解决什么

发布、热修、同步环境这类流程，本质都是「一串有序的分支创建与合并」。硬编码一套流程不够用，
所以这里把它抽象成模板：

```
模板 = 变量声明 + 有序步骤
步骤 = 建分支(create) / 合并(merge) / 推送(push) / 打标签(tag) / 拉取(pull) / 提交(commit)，
       分支名、标签名、提交说明都可写死也可用 {变量}
`push` 只把指定分支推到远端，不合并——适合「先把功能分支推上去，再合进目标分支」这种流程
`tag` 在指定分支的最新提交上打轻量标签（不切换分支、不改工作区）；勾选「推送标签」会同时把标签推到远端
`pull` 把指定的本地分支更新到远端最新（分叉时按「分叉时」策略；本地没有则建同名跟踪分支），不动其它分支
`commit` 提交工作区里的全部改动（含未跟踪的新文件，.gitignore 忽略的除外），步骤填的「目标」就是提交说明；不推送
```

实例：默认的发布模板

| 变量 | 说明 |
| --- | --- |
| `{base}` | 基础分支，从仓库现有分支里选 |
| `{feature}` | 要合入的功能分支，按 `feature/*` 过滤 |
| `{release}` | 发布分支名；**由 `{feature}` 推导**：`feature/v1.0.1` → `release/v1.0.1` |
| `{tag}` | 版本标签名；**由 `{feature}` 推导**：`feature/v1.0.1` → `v1.0.1` |

变量之间可以推导：在模板编辑器里给变量配一条「自动」规则
（`来自 feature` + `取 / 之后` + 前缀 `release/`），选中功能分支时发布分支就自动填好。
一旦你手改了被推导的字段就停止跟随，把它清空又会恢复跟随。
可取片段的方式有三种：`取 / 之后`、`取最后一段`、`整个值`。

| # | 步骤 |
| --- | --- |
| 1 | `create` 从 `{base}` 创建 `{release}` |
| 2 | `merge` `{feature}` → `{release}` |
| 3 | `merge` `{release}` → `deploy-pre-default/test`（推送） |
| 4 | `merge` `{release}` → `deploy-prod-default/test`（推送） |
| 5 | `merge` `{release}` → `develop`（推送） |
| 6 | `merge` `{release}` → `master`（推送） |
| 7 | `tag` 在 `{release}` 上打 `{tag}` 标签（推送标签） |

这套顺序、目标分支、是否推送全部可以改；也可以新建别的模板（热修、回滚、多环境同步……），
两个模板互不影响。

## 界面

右侧栏会话级标签页，深色玻璃 + 网格底纹 + 霓虹青紫描边的 HUD 风格；步骤按「管线」纵向排列，
节点随状态变色发光，执行中的一步有扫描动画。视觉集中在 `client/client.js` 顶部的 `CSS` 常量里，
底色与文字复用宿主的 `--dsw-*` 变量，因此浅色主题下自动降级为蓝图配色；`prefers-reduced-motion`
下关闭全部动画。

两个页签：

**执行**
0. 「刷新」只重读本地状态；「拉取」执行 `git fetch --prune origin`，更新各分支的 `↓落后` 并清理远端已删分支。
   只 fetch，不动工作区、不改本地分支，随时可点。拉取旁边是「提交」：弹层里先列出工作区里的改动文件
   （类型徽标 + 复选框，默认全选，可全选/全不选），勾选要提交的文件并填提交说明后确认；
   提交按文件粒度执行 `git add --all -- <勾选的文件>` + `git commit`，含未跟踪的新文件（`.gitignore` 忽略的除外）。
   没勾选的已暂存文件会先退出暂存区，不会混进这次提交。只提交到本地、不推送，合并/变基未完成时禁用。
   每个文件行右侧还有「diff」：点开查看该文件 **HEAD ↔ 工作区** 的对比，可切换「统一 / 并排」两种视图，
   带新旧行号与 `+/-` 行统计；二进制文件只提示类型，超长 diff 只展示前 2000 行。
   状态行分别显示已跟踪改动与未跟踪数量；改动超过 500 项时只列出前 500 项，未列出的不会提交
1. 「分支」区块按 `/` 折叠成**目录树**（例如 `feature/` 下挂各功能分支），当前分支所在目录自动展开；
   点目录行展开/收起，也可以一次「展开全部 / 收起全部」。叶子只显示最后一段，悬停可看完整分支名。
   本地分支与只在 `origin` 上存在的分支（标「远端」）放在同一棵树里，并显示当前分支与能不能切换：
   **左键点分支 = 切换当前分支；右键点分支 = 弹出「用模板执行」菜单**。分支多时列表内部滚动
2. 右键选中某个模板后弹出**执行窗口**（见下），确认参数与完整流程后才真正开始
3. 窗口里按顺序执行；某步失败即停，解决后可「从失败处重试」。失败摘要直接写原因与处理建议
   （凭据缺失、网络不可达、分支受保护、非快进被拒等），并自动展开这一步的 git 原始输出；
   失败结果持久化到 `~/.dsh/git-flow/last-run.json`：重开面板或重启应用后，面板顶部仍显示
   「上次执行失败」横幅，可「重试这一步」（重新打开执行窗口并从失败步骤开始）或「忽略」
4. 「执行完切回原分支」（默认开启，在执行窗口里勾选）：步骤会 checkout 到各个目标分支，跑完自动切回
   开始前所在的分支；本来就在该分支上时直接算成功（工作区有改动也不影响）。需要真正切换时才走安全
   检查——工作区有改动、合并未完成、原分支已删除都会跳过并说明原因
5. 关闭窗口后，面板底部保留本次执行日志；已完成的分支与合并会自动跳过，整条流程可重复运行

**分支**
- 分支按名称里的 `/` 分层显示成目录树：目录行前是文件夹图标（展开/收起两种形状），只负责
  展开/收起（不切换分支），叶子是具体分支；当前分支所在目录链默认展开，其它目录默认收起，
  也可以在列表底部一次展开/收起全部
- 叶子只显示最后一段（如 `feature/` 下的 `aasp-V1.1.0`），悬停可见完整分支名；点击、右键用的都是完整名
- 本地分支可直接点；`origin` 上独有、本地还没有的分支标注「远端」，点它切换时自动创建同名
  本地跟踪分支（列表来自本地已有的远端引用，想看最新列表先点「拉取」）
- 右键任意分支 → 菜单里列出模板，选中即打开执行窗口；右键的分支会作为模板里**最匹配** `pick` 变量
  的默认值（通配符越具体越优先，例如 `feature/v1.0.1` 落到 `feature/*` 而不是 `*`），release/tag
  等推导字段随之补齐，窗口里仍可改
- 已跟踪文件有改动、合并/变基未完成、目标分支不存在时拒绝切换并说明原因；未跟踪文件会跟随到新分支
  （git checkout 的原生行为）；切分支不 stash、不丢弃改动
- 右键菜单里也有「切换到此分支」，和左键等价

**执行窗口**
- 打开时显示模板参数（`pick` 下拉 / `input` 文本框）、解析后的完整流程、以及「执行完切回原分支」
- 模板里有 `提交` 步骤时，窗口里会多出「提交说明」输入框：默认取模板内容（变量会解析成实际值），
  可以直接改成本次执行的说明；删光后不会自动回填，可以重新输入，点「↺ 模板」才恢复模板内容。
  所以提交信息不必写死在模板里
- 必填参数没填齐时「执行」禁用；「取消」直接关闭，不改仓库
- 点「执行」后同一窗口切换成进度视图：逐步显示状态、git 原始输出与日志；合并冲突时窗口里给出冲突文件
  和「继续 / 中止」
- 跑完显示「执行完成 / 执行失败」；失败时「从失败处重试」只跑剩余的步骤，成功后可「关闭」
- 执行中窗口不能关闭（没有中止语义），跑完自动停在结果页

**模板**
- 竖排列表，一行一个模板；点某一行在它下方展开这个模板的完整配置（名称、变量、步骤、预览）
- 再点已展开的行即收起；收起只是隐藏表单，草稿仍在内存里，再点开还是刚才的改动
- 收起时行头会标「未保存」，提醒你有改动还没保存
- 行头标出「新的」（还没保存）/「未保存」（改过没存）/「有问题」（校验失败）
- 新建 / 复制 / 删除模板 / 恢复默认
- 编辑变量：key、显示名、`选分支` 或 `手填`、过滤通配符、默认值
- 编辑步骤：`建分支`/`合并`/`打标签`/`推送`/`拉取`/`提交`、来源、目标
  （打标签步骤这里填标签名，`拉取` 步骤填要更新的分支，`提交` 步骤填提交说明）、是否推送
  （只有 `建分支`/`合并`/`打标签` 有推送勾选）、上移/下移/删除
- `提交` 步骤的提交说明支持插入模板变量：点输入框右侧 `▾` 选 `{变量}`，会插到光标处
  （也可直接手打）；同一个变量已经写进文本后，下拉里会置灰并标「已插入」，不能重复插入，
  不同变量仍可继续插入。提交只写本地，要推送再加 `推送` 步骤。执行时还能在弹窗里按次覆盖
  这段说明，不会改模板
- 步骤的「来源 / 目标」是**可点选的下拉**：点输入框或右侧 `▾` 列出「模板变量 `{key}`」和
  「仓库现有分支」，输入关键字即过滤；右侧标记当前值属于 `变量` / `分支` / `手填`。
  仍允许直接手填本次要新建、暂时不存在的分支（如 `release/1.0.6`）
- 按默认值实时预览每一步会变成什么分支
- 保存到 `~/.dsh/git-flow/templates.json`
- 模板区右上角的「↻ 重读」随时从磁盘重读模板（AI 保存新模板后点它即可，不用重开面板）

## AI 集成：`/add-template` 与模板工具

除了手动编辑，也可以直接让 AI 建模板：

- 在对话框输入 `/add-template <需求>`（`/` 菜单里自动出现）。命令会把需求交给当前会话的 AI，
  AI 先只读地查看仓库分支、列出模板摘要和你确认，然后调用工具保存。
- AI 可用的工具：
  - `git_flow_add_template`：新增/更新模板。保存前跑与面板相同的校验；`id` 已存在时默认拒绝覆盖，
    需显式传 `overwrite: true`；写入走串行读-改-写 + 临时文件 + rename，失败不会留下截断的 JSON。
  - `git_flow_list_templates`：列出已保存模板（id、变量、步骤、无效原因），便于新增前先看现状。
- 工具与面板共用同一份模板存储和同一套校验，因此 AI 写坏数据不会波及已有模板。
- 这些是服务端能力：**改代码后必须重启 DeepSeek Harness 才会出现命令与工具**（客户端改动热更新，服务端不会）。

## 设计要点

- **只做原语**：引擎只提供「建分支」「合并」「推送」「打标签」「拉取」「提交」，流程顺序完全由模板决定，
  没有写死 develop/master/deploy 之类的概念。
- **前端驱动执行**：一次请求只执行一步，所以每步都有独立状态，失败时前面的成果保留。
- **幂等**：分支已存在则跳过创建；目标已包含来源则跳过合并。整条流程可重复运行。
- **每步先同步远端再动手**（`git fetch --prune origin` + 必要时快进）：

  | 步骤 | 同步什么 | 为什么 |
  | --- | --- | --- |
  | 建分支 | 起点分支 | 新分支从最新代码长出，而不是从过期的本地副本 |
  | 合并 | 来源分支 + 目标分支 | 来源落后会合进旧内容；目标落后会让推送被拒 |
  | 推送 | 要推的分支 | 本地落后时 push 会被远端拒绝 |
  | 打标签 | 只 `fetch`，不切分支也不快进 | 让只在远端存在的分支也能解析到；标签指向本地分支最新提交，与工作区改动无关 |
  | 拉取 | 目标分支 | 把本地分支同步到远端最新；已最新或没有同名远端分支时跳过 |
  | 提交 | 不 fetch | 提交只写本地，与远端无关；没有可提交的改动时跳过 |

  本地与远端分叉（两边都有新提交）时的处理由模板的「分叉时」决定，三选一：
  - **merge（默认）**：`git merge origin/x`，留一个合并提交，历史保留分叉与汇合
  - **rebase**：`git rebase origin/x`，本地提交重放到远端之上，历史线性、无合并提交
  - **ff**：只快进，分叉就停下并提示手动处理，不产生任何提交

  merge / rebase 出冲突时该步失败并列出冲突文件，仓库停在合并或变基中途，
  可用面板的「继续 / 中止」收尾（底层分别是 `merge --continue` / `rebase --continue`
  与 `merge --abort` / `rebase --abort`）。

  冲突期间面板每 3 秒自动重读一次：还有未解决文件时「继续」是禁用的，
  解决并 `git add` 后会自动变可用。若你在外部工具里直接**提交**了合并，
  操作结束后横幅会消失，执行窗口里的冲突块也会消失，点「从失败处重试」即可收尾。
- **不自动解决冲突**：有冲突时该步失败并提示「需手动解决后重试」，不做 rebase、不做 squash。
- **拉取分支**：`pull` 先 `git fetch --prune origin`，再把指定本地分支按「分叉时」策略同步到远端最新；
  本地没有同名分支时创建一个同名跟踪分支（不切工作区）。已是最新、或本地有但远端没有同名分支时该步跳过。
  工作区有未提交改动**不会**直接拒绝：快进或只更新引用时可以带着改动完成，只有改动与远端更新冲突、
  或需要切换/变基时 git 才会拒绝，此时提示先提交或 stash。
- **提交步骤**：`commit` 提交工作区全部改动（含未跟踪的新文件），提交说明来自步骤的「目标」字段；
  执行弹窗里可以按次修改这段说明（不改模板）。没有可提交的改动时该步跳过；只提交到本地，要推送就再加 `push` 步骤。
- **安全边界**：仓库路径只来自会话自身的工作目录，请求体里传的路径不采信；所有路由都过宿主的
  连接可信面；提交只接受改动列表里真实存在的文件路径；已跟踪文件有未提交改动时拒绝切分支；
  「分支」列表的切换只接受本地或 `origin` 上真实存在的分支名，`origin` 独有则建本地跟踪分支；
  模板执行只能从分支右键菜单发起，并且要在执行窗口里确认参数与流程后才开始。

## 误删与恢复

模板删除后不可直接从磁盘找回，因此有三层保护：

1. **删除要连点两次**：第一次按钮变成「确认删除？」，再点才真删。
2. **每次保存前自动备份**：旧文件复制到 `~/.dsh/git-flow/backups/templates-<时间戳>.json`，保留最近 20 份。
   需要手动找回时，从那里挑一份复制回 `~/.dsh/git-flow/templates.json` 即可。
3. **内置默认模板可一键恢复**：模板列表为空时会出现「恢复默认模板」按钮，
   也可以随时从接口 `/git-flow/templates/restore-default` 加回来。

另外，读到校验失败的模板不再静默丢弃：会带着失败原因保留在文件里，界面标「这个模板有问题」
并拒绝保存，避免一次自动保存就把坏数据永久抹掉。

## 已知限制

- 同一时刻只执行一个模板的一次运行，没有历史记录与并发保护。
- 执行窗口不提供中止正在进行的步骤：点「执行」后会一直跑到某步失败或全部完成（失败即停）；
  执行中窗口不能关闭。
- 模板是全局的（跨仓库共享），按分支名匹配；不同仓库分支命名差异大时需要建多个模板。
- 不做 cherry-pick、不自动解决冲突；`rebase` 只用于「分叉时」同步远端，不会把 rebase 当成合并步骤。
- `tag` 打的是轻量标签（等同 `git tag <标签名> <分支>`），不写注释、不记录打标签人；标签已存在时跳过创建，
  分支不存在时该步失败。不提供删除、改名标签的能力。
- 面板的「提交」按文件勾选提交（含未跟踪的新文件），不做行级/分块暂存；只提交到本地，推送仍走模板步骤或手动。
  模板里的 `commit` 步骤不同：提交工作区**全部**改动，不能按文件勾选，提交说明写在模板里（可用变量）。
- `pull` 步骤在本地分支落后时通过更新引用完成快进，只有分叉且 merge/rebase 时才会临时 checkout 到目标分支；
  工作区有未提交改动不再直接失败：不冲突的改动会保留并完成拉取，只有改动与远端更新冲突或需要切换/变基时
  才失败，并提示先提交或 stash。
- 切分支不做 stash：已跟踪文件有改动时直接拒绝；未跟踪文件会跟随到新分支（`git checkout` 的原生行为）。
  远端独有的分支会被建成同名本地跟踪分支，不会自动 fetch，先把远端引用拉新再切换。
- diff 预览对比的是 HEAD 与工作区（也就是勾选后会提交的内容）；二进制文件、符号链接和超过 5 MB 的未跟踪文件不展示内容，只给提示。
- AI 工具和 `/add-template` 是 profile 级注册：同一 profile 的所有会话都能调用，写入的是跨仓库共享的模板文件。

## 合并冲突怎么处理

合并撞上冲突时，那一步会变成「失败」，流程停下（前面的步骤成果保留）。执行窗口里会列出冲突文件，
面板顶部也会出现红色横幅：

1. 列出**具体哪些文件**冲突（`UU` 状态的路径）
2. 你可以二选一：
   - **在终端/编辑器解决** → `git add` → 回到面板点「刷新」，「继续合并」自动变可用 → 点它收尾
   - **点「中止合并」** → `git merge --abort`，工作区还原到合并前

「继续合并」在还有未解决文件时是禁用的，避免把带冲突标记的文件提交进去。
收尾用的是 `git commit --no-edit`，不会弹编辑器。
- 执行过程没有事务语义：中途失败时已完成的步骤不会回滚（这是有意为之，便于人工判断）。
